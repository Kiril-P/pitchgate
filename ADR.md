# Architecture Decision Record

## 1. Backend language and framework
Date: 2026-09-28
Status: Superseded by [7] for storage (SQLite became SQL Server); Flask and `urllib` still hold
Context: The app is one process that serves pages, reads and writes SQLite, and calls external model APIs. It has to stay small enough to explain on paper, with no notes, at the comprehension check.
Decision: Python with Flask. Flask serves the HTML and the routes in the same process, and SQLite stays in the standard library. External APIs are called with the standard library's `urllib`, not vendor SDKs.
Alternatives considered: FastAPI. It is a strong fit for a JSON API, and it was rejected because this app is a small server-rendered site. The extra API machinery would be surface area to explain without buying a feature the club needs. Django was rejected because the app does not need its admin, auth, or ORM. For HTTP, `requests` and vendor SDKs were rejected because each API is one POST with a JSON body, and every extra package counts toward the dependency cap.
Consequences: Routing and templates stay thin. Domain rules live in `pitchkitchen/ideas/` and `pitchkitchen/review/`, which keeps the framework choice from spreading into the business logic. A later service split can keep those two packages and drop the Flask layer on one of them. Timeouts and error handling for each API are written by hand in one file per API.
Update 2026-10-01: Chef was planned on OpenAI, but the account had no API credits. Because `review/coach.py` posts plain OpenAI-style chat JSON with `urllib`, moving Chef to Google Gemini's OpenAI-compatible endpoint only needed a configurable `COACH_URL`. No SDK had to be swapped. The free tier is often overloaded, so `COACH_MODEL` takes a comma-separated list and Chef tries the next model when one is busy.
Update 2026-10-04: Beginners need facts before they can find people to talk to, so Chef can search the web. `find_facts` in `review/coach.py` calls Gemini's own `generateContent` endpoint with the `google_search` tool instead of the OpenAI-compatible one, because its `groundingMetadata` ties each sentence to a source link; `parse_facts` drops every sentence without one, so the founder only sees facts they can check. This is the one Gemini-only call. On 2026-10-04 the free-tier key had no Google Search quota (every search call returned 429 while plain calls still worked), so when search fails `suggest_searches` asks Chef for queries only, and the page builds plain Google search links from them; the founder then adds what they find with its link.

## 2. Ideas and review meet only at a revision id
Date: 2026-09-29
Status: Decided
Context: The app needs two domains that can be split later. A verdict is about one exact version of what the founder wrote, and the ideas package should not own the cutoff rules or know which models are called.
Decision: `pitchkitchen/ideas/` stores everything the founder wrote. `pitchkitchen/review/` stores everything the app says back: Jev's scores, the label, and later Chef's questions. The only shared key is `revision_id`. Routes in `pitchkitchen/pages.py` save the revision first, then pass review the revision id and a snapshot of the founder's text.
Alternatives considered: Keep the label columns on `revisions`. That needs one less join, and it was rejected because a verdict change would sit in the idea table and the two domains could not be split without cutting that table apart. Putting Chef in its own third package was also rejected, because Chef's question depends directly on Jev's scores and the two would always be called together.
Consequences: An idea can be saved when Jev is down. The verdict row is still written, with label PENDING. A later service split can move `pitchkitchen/review/` out as one service that takes a revision id and text and returns a verdict.
Update 2026-10-01: Chef is built inside review. `review/service.py` runs one round (Jev, then the rules in `review/logic.py`, then Chef in `review/coach.py`) and stores Chef's reply in `chef_messages`, keyed by `revision_id` like `verdicts`. The idea's status (cooking, parked, served, binned) stays in ideas, and `pages.py` sets it from what review returns. Deleting an idea is also done in `pages.py`: review forgets its rows first, then ideas deletes the revisions, so neither package reaches into the other's tables.
Update 2026-10-03: The product now targets a venture lab, so it needs evidence logs and an organizer view. Logged customer conversations are founder text, so the `evidence` table lives in ideas. The tasting gate is a judgment, so `gates` lives in review and keeps only `idea_id` and `last_evidence_id`; review receives the logs as a text snapshot inside `founder_text` and never reads `evidence`. A third package, `pitchkitchen/cohort/`, turns plain dicts into organizer metrics. It has no tables and imports neither ideas nor review; `pitchkitchen/organizer.py` builds its input from both stores, the same way `pages.py` composes the other two.
Update 2026-10-04: Three simulated founders (no idea, an idea, real pilots) run through the live app all ended with nothing they could build from, and the beginner had only the one-liner suggestions to start with, so ideas now have a starting level and every idea can export a starter pack for Claude Code. Facts found online are founder-gathered evidence, so they live in the ideas `evidence` table with `kind = 'fact'` and a source link. Review gets the level and session as plain values and decides the starter gate itself (`starter_gate`); serving counts only conversations. Chef's plan is stored by review as a `starter_pack` message, and `pitchkitchen/pack.py`, pure like cohort, renders the Markdown and copies the evidence section from the logs rather than from Chef, so a pack can't cite something that was never logged.

## 3. The conversation is a tree of revisions
Date: 2026-09-29
Status: Decided
Context: The founder pitches once and then answers questions. Each answer is scored together with everything before it, and editing an earlier answer later must not erase text that was already scored.
Decision: `revisions` holds both kinds of founder text. A pitch row has the one-liner and story and no parent. An answer row has the answer and a `parent_id` pointing at the revision before it. A CHECK constraint enforces which columns each kind fills. The current conversation is the newest revision and its chain of parents.
Alternatives considered: A separate `answers` table with a position number under one pitch row. It is simpler to list, and it was rejected because editing answer 2 would either overwrite scored text or need a version column on every answer. With `parent_id`, an edit is a new sibling and old verdicts still point at the exact text they judged.
Consequences: Each `verdicts` row references one revision, which fixes the exact branch that was judged. Rebuilding a conversation walks parents in Python (`walk_branch`), which is fine at club scale but would need a recursive query for very large trees.
Update 2026-10-03: Edits are now built. `edit_answer` inserts a sibling with the same `parent_id`, so it becomes the newest revision and the branch follows it; the old answer and its verdict stay in the tree. The schema grew to match the evidence loop: `ideas` gained `token`, `tone`, `pivot_of`, `shared`, and `consent_at`; ideas owns a new `evidence` table; review owns a new `gates` table, `verdicts` gained `evidence` and `answered`, and `chef_messages` accepts `homework` and `next_steps`. `ensure_schema` migrates older files in place, including renaming KILL, FIX, and SHIP to UNPROVEN, PARTIAL, and PROVEN.
Update 2026-10-04: `ideas` gained `level` (new, idea, tested), `evidence` gained `kind` (conversation, fact) and `source`, and `chef_messages` accepts `starter_pack`. Old rows become `idea` and `conversation`, and `ensure_schema` adds the columns in place; a fact reuses `who` for the site and `quote` for the sentence instead of a separate table, because the gate, the session limit, and the logs list treat both kinds the same.

## 4. Tests use fake Jev and Chef, never the network
Date: 2026-10-01
Status: Superseded by [9] for the test database (in-memory SQLite became a throwaway SQL Server); the fake Jev and Chef still hold
Context: Every round calls two external APIs. Jev costs credits per call. The free Gemini tier used for Chef returns "high demand" errors several times an hour. The brief needs at least 70% coverage, and the tests have to pass on a fresh clone with no keys.
Decision: `jev.judge` and the functions in `review/coach.py` take an optional `transport` argument: a function that receives the request body and key and returns the parsed JSON. Tests pass small fakes from `tests/fakes.py` (`FakeJev`, `FakeChef`) that return payloads shaped like the real replies, and `create_app` accepts `JEV_TRANSPORT` and `CHEF_TRANSPORT` so the page tests in `tests/test_loop.py` can drive a whole interview through the Flask test client. The database is an in-memory SQLite connection for store and service tests and a `tmp_path` file for page tests.
Alternatives considered: Patching `urllib.request.urlopen` with `unittest.mock`. It needs no change to the code, and it was rejected because each test would have to fake HTTP responses and byte bodies instead of the JSON the code actually reasons about, so tests would break whenever the request plumbing changes. Recording real responses with a library like `vcrpy` was rejected because it adds a dependency and stores API replies in the repo. Calling the real APIs in tests was rejected because it costs credits, needs keys, and fails whenever Gemini is overloaded.
Consequences: The suite runs in under a second with no keys and no network. Rules, branch walking, the round service, and every ending (cap, two KILLs, serve, park, delete, Chef failing and retrying) are covered. The two `_post` functions are the only untested code; they were checked by hand against the live APIs on 2026-10-01, and the fake Jev payload was updated then to include the `probabilities` field that `parse_answers` now reads.
Update 2026-10-03: `FakeJev` now returns `evidence` and `answered`, and answers tasting calls with a separate gate payload so one fake can drive a whole journey: five answers, homework, three logs, a sent-back gate, a passed gate, and session two. `FakeChef` picks its reply from the JSON shape Chef was asked for (turn, homework, one-liners, or served pitch). The organizer metrics in `cohort/logic.py` are pure functions tested with plain dicts and a fixed date. The suite is 111 tests at 97% coverage.
Update 2026-10-04: The first real founder was binned after two answers and four minutes, before the app ever sent them to talk to customers. Both answers dodged Chef's question, but `all_weak` ran before `dodged`, and `next_step` binned inside session 1. The fakes missed it because each test checked one rule on its own payload, not what a vague real answer triggers in order. `decide` now checks `dodged` before the scores, and `next_step` only bins inside a session after a passed gate. The real founder's scores became a `decide` test, and page tests pin that a weak first session stays open and that binning needs a gate first. The suite is 113 tests at 97% coverage.

## 5. No login or idea ownership
Date: 2026-10-02
Status: Decided
Context: Pitch Kitchen is used by one student founder club, where members pitch in the same room and want to read and push on each other's ideas. Every hour spent on accounts is an hour not spent on the interview, and the deadline is 2026-10-04.
Decision: There are no accounts. A founder types a display name with each pitch, and anyone with the link can open, continue, park, serve, or delete any idea.
Alternatives considered: Email and password login with Flask sessions and an `owner_id` on `ideas`. It would stop one member from deleting another's idea, and it was rejected because it adds a `users` table, password hashing, session handling, and an ownership check on every route, none of which makes the verdict or Chef any better. A magic-link login was also rejected, because it needs an email provider, which is an external runtime dependency the club doesn't need.
Consequences: The app relies on club trust: anyone can delete anyone's idea, and the forms have no CSRF protection, so it must not be exposed to the public internet as-is. Because ideas and review only meet at `revision_id`, adding an `owner_id` on `ideas` later touches the ideas package and the routes, not review.
Update 2026-10-03: Still no login, but ideas are no longer public by default. A market check showed founders won't pitch where anyone can read and delete their idea. Each idea now lives at a random `/i/<token>` link; the home page lists only tokens stored in this browser's cookie, plus ideas a founder chose to share on the cohort board. Organizers read everything through `/organizer`, gated by `ORGANIZER_KEY`, and the pitch form asks for consent to that and to the AI providers. Anyone holding a link can still act on that idea, so links must not be posted publicly.

## 6. The split: ideas calls review over HTTP, and the seam from ADR-2 held
Date: 2026-11-18
Status: Decided
Context: Assignment 2 needs one service per domain, each with its own database, and at least one user flow that crosses between them on the server. In the monolith, `pages.py` read both stores in one process; that composing now has to happen over HTTP.
Decision: `services/ideas` owns ideas, revisions, evidence, the starter pack Markdown and the cohort metrics, and is the service the UI talks to for everything about an idea. When a founder pitches or answers, ideas saves the revision first, then calls review (`POST /rounds`) with the revision ids and a snapshot of the founder's text; review owns verdicts, gates, Chef's messages and the Jev call log, and all the rules. The UI calls review directly only for Chef's Prep suggestions, which touch no idea.
Alternatives considered: Composing in the browser, with the UI calling both services and merging their answers. It would make each service simpler, and it was rejected because the order matters: an answer may only be saved if review says the session is still open, and a saved revision must then be scored. Leaving that order to JavaScript in the browser means a closed tab can leave a revision that is never scored. Moving the seam so Chef became a third service was rejected for the same reason as in ADR-2: Chef's question depends on Jev's scores and they are always called together.
Consequences: ADR-2 held, with one correction: besides `revision_id`, review also keys gates and the Jev budget by `idea_id`, so both ids cross the seam as plain numbers with no foreign key. Every outbound call has a timeout (5 seconds, or 90 when Jev or Chef is involved). When review is down, a new pitch is still saved and an idea's page still loads with the founder's own text and a notice; writes that need review's judgement (answers, gates, serving, deleting) are refused with a 503 and save nothing.
Update 2026-11-21: The provided `system.schema.json` caps every call between services at 30 seconds, so the long timeout is now 30, not 90. A round is one Jev call (12 s) and one Chef step with a 16 s budget; Chef only tries the next Gemini model if that try can still finish inside the budget. A round that still runs over keeps the founder's answer: review finishes it and the verdict shows on the next page load.

## 7. One database per service, versioned SQL migrations, and no foreign key across the seam
Date: 2026-11-21
Status: Decided
Context: Assignment 1 kept all seven tables in one SQLite file and changed the schema on boot with `ensure_schema`, which added missing columns and, once, rebuilt `chef_messages` to widen a CHECK. Assignment 2 needs one SQL Server database per service, a login per service that cannot reach the other database, and schema changes that run once each and keep the rows already there.
Decision: Ideas keeps `ideas`, `revisions` and `evidence`; review keeps `verdicts`, `gates`, `chef_messages` and `jev_calls`. The schema of each is a folder of numbered SQL files (`migrations/001_init.sql`, then `002_…`), applied in name order at startup by a 50-line runner (`migrations.py`) that records each file in `schema_migrations`. Each file runs in one transaction together with its record row, so a failing file leaves no half-applied schema and is retried on the next start. Applied files are never edited; a correction is a new file. No Assignment 1 data was moved: the SQLite files only held test pitches, so both databases start empty. Neither service has seed data.
Alternatives considered: Alembic. It records versions the same way and can generate migrations, and it was rejected because the stores are raw SQL with no SQLAlchemy models, so it would add SQLAlchemy and Alembic to each service only to run SQL files. Keeping `ensure_schema` was rejected because it decides what to change by inspecting the live tables, so two databases can end up with different histories and nothing records what ran. Keeping the foreign keys by putting review's tables in the ideas database was rejected because the assignment requires each service to own its data and connect only to its own database.
Consequences: Three foreign keys from review to `revisions` are gone (`verdicts`, `chef_messages`, `jev_calls`), so review stores whatever revision and idea ids ideas sends. This is compensated in three ways: review is only called by ideas, never with ids the UI made up; deleting an idea asks review to forget its rows first and deletes nothing if review is down, so no scores outlive their revisions; and SQL Server `IDENTITY` never hands out a deleted id again, so a leftover verdict could never attach to a new revision. SQL Server also needed small fixes SQLite never asked for: `rule` is a reserved word and is quoted as `[rule]`, `INSERT OR REPLACE` became a delete and insert in one transaction, and new rows return their id with `OUTPUT INSERTED.id`. Migrations run in gunicorn's master process (`--preload`) and Container Apps runs at most one replica, so two runners never race. Recovery from a bad migration is forward-only: a file that fails rolls back, the new container never passes `/health`, the deploy job fails, and the previous revision keeps serving until a new numbered file fixes it. A file that succeeds but damages data is undone with Azure SQL point-in-time restore into a new database, from which the rows are copied back, followed by a corrective migration; to keep that rare, migrations only add or backfill columns and never drop one in the same release that stops using it.

## 8. Serverless on Azure: Container Apps that scale to zero, free serverless SQL, and a storage static website
Date: 2026-11-22
Status: Decided
Context: The system must run on Azure for Students with nothing billed while idle, inside a fixed allowance: two Container Apps in one environment, two serverless SQL databases on one server, one storage account for the UI, and the managed identity the pipeline signs in as. Every resource lives in `rg-kpetrovski-ieu2024` in `francecentral`, one of the five regions the subscription allows.
Decision: The UI is a static website on the storage account `kpetrovskiieu2024ui`, billed per GB stored and served. Each service runs as a Container App on the Consumption plan (`kpetrovski-ieu2024-ideas`, `kpetrovski-ieu2024-review`) with 0.25 vCPU, 0.5 GiB, and 0 to 1 replicas, billed per vCPU-second and GiB-second only while a replica runs. Each service has its own General Purpose serverless Gen5 database (0.5 to 1 vCore) on `kpetrovski-ieu2024-sql`, on the free offer, which pauses after 60 idle minutes and pauses instead of billing when the monthly free vCore-seconds run out. Images live on GitHub Container Registry as public packages, so the apps pull them without registry credentials. The environment has no Log Analytics workspace (`--logs-destination none`): it is not in the allowance, and logs are read by streaming instead, with the deploy job printing each new revision's startup log, migration line included, into the Actions run where it stays. The pipeline signs in as the managed identity `kpetrovski-ieu2024-github` through OpenID Connect, trusted only for runs on `main` and with Contributor on this resource group only, so no Azure password exists anywhere. Database passwords and API keys are GitHub secrets that the pipeline sets as Container Apps secrets, referenced with `secretref:`; they are never plain environment variables.
Alternatives considered: Azure Container Registry: private images and pulls inside Azure, rejected because even the Basic tier has a fixed monthly cost, and GHCR is free. Keeping one replica always on (`min-replicas 1`): no cold starts, rejected because it bills around the clock for a cohort tool used a few hours a week. A Log Analytics workspace for logs: searchable history after a replica is gone, rejected because it is a resource outside the allowance and the one log line the report needs is kept in the Actions run instead.
Consequences: The first request after a quiet period is slow. The replica starts (a 49 MB image, then gunicorn builds the app once and runs migrations), and if the database has paused it needs up to a minute to resume, during which connections fail; startup therefore connects up to 8 times with backoff from 2 to 20 seconds, and each request retries 3 times. Container Apps answers a request that waits longer than about 30 seconds with a 503 and no CORS headers, so the browser sees a network error; the UI turns both into one designed message ("The kitchen is waking up… try again in a moment") instead of a blank page. Because ideas calls review, a cold system can wake ideas first and then time out waiting for review to wake: the page then loads without scores and offers "Load the scores again", which is the same degraded state as review being down. Migrations at startup are safe only because there is at most one replica and gunicorn's `--preload` runs them once per container. At 100 times the traffic this changes: `min-replicas 1` on both apps to remove cold starts (a fixed cost now worth paying), `max-replicas` above 1, which means moving migrations out of startup into a pipeline step or a Container Apps job that runs once before the new revision takes traffic, more vCores or a provisioned database once the free monthly allowance is used up, and a queue for Jev and Chef rounds, which hold a gunicorn thread for up to 28 seconds each (see ADR 10).
Update 2026-11-24: The infrastructure is now code. `infra/main.bicep` defines the storage account, the SQL server, its firewall rule, both databases, the Container Apps environment and both apps, and the deploy job applies it with every release, with the image tags and secrets as parameters; it replaced the `az containerapp secret set` and `update` calls. Before the switch, `az deployment group what-if` against the live group showed no change except read-only fields. Bicep over Terraform: Terraform keeps a state file, which on Azure means another storage account outside the allowance plus state locking, while Bicep's state is the resource group itself, and Bicep is Azure's own language with no provider to pin. Bicep over the CLI commands it replaced: the template is declarative and idempotent, so a manual change in the portal is undone by the next deploy, and the whole setup reads as one file. Still one-time commands: the providers, the pipeline's identity and every role assignment (Contributor cannot grant roles), the static website switch and the contained database users, which are data-plane settings. The cost: every deploy re-applies the whole template, including the SQL admin password, which is now a GitHub secret as well.

## 9. CI gates every change on lint, a real SQL Server, coverage, the system description and the images; one cross-seam suite runs both services over HTTP
Date: 2026-11-23
Status: Decided
Context: Assignment 2 deploys every merge to `main` with no manual step, so whatever CI lets through reaches the live URL. The split also added failure modes a single process never had: SQL Server dialect differences, two databases, HTTP between the services with timeouts, and documents (`system.yaml`, OpenAPI) that can drift from the code.
Decision: `ci.yml` runs on every push and pull request and is called by `deploy.yml` with `workflow_call`, so a deploy only happens after CI passed on the same commit; its seven jobs are required checks on `main`, which accepts changes only through pull requests. The jobs: ruff with pyflakes, pycodestyle, import order and bugbear (bugs, not style); each service's tests against a throwaway SQL Server 2022 container whose password is generated per run and masked, failing below 70% coverage (the services sit at 96 to 98%); the cross-seam suite; validation of `system.yaml` against the provided schema and of both OpenAPI documents against the specification; and a build of both images. Drift is tested, not only validated: each service compares its Flask URL map with its OpenAPI paths, and a root test checks that `system.yaml` lists exactly the variables `load_config` reads, with the same defaults, and that every endpoint ideas calls exists in review's document. The cross-seam suite (`tests/integration/`) starts the real review app on a local port with werkzeug and drives the real ideas app against it, so ideas talks to review through its own `http_transport` with its real timeouts and both services use their own databases. Only Jev and Chef are faked, inside review, as in ADR 4. The 16 founder journeys from Assignment 1 run this way, plus one with review stopped (its URL pointed at an unused port).
Alternatives considered: Running the cross-seam test against `docker compose up` in CI. It is closer to production, and it was rejected because it needs both images built and SQL Server started inside compose on every run for the same HTTP path the in-process servers already take; the compose stack is checked by hand from a clean clone instead. Replacing review with a stub in the cross-seam test was rejected for that suite because a stub only proves ideas agrees with the stub, not with review; stubs are used in the ideas unit tests instead, where they make timeouts, refusals and garbage replies easy to produce. Testing on SQLite, as in Assignment 1, was rejected because three real bugs only appear on SQL Server: the reserved word `rule`, `OUTPUT INSERTED.id` instead of `lastrowid`, and identities that do not restart when rows are deleted.
Consequences: A red test, a coverage drop, a route missing from OpenAPI or an undocumented variable blocks the merge, and therefore the deploy. The deploy's own health check waits for `/health` to report the new commit, so a revision that never starts fails the run while the old one keeps serving. Deliberately not tested: the real Jev and Gemini HTTP calls (`_post` and `_send`, checked by hand against the live APIs), the UI's JavaScript (no browser tests; checked by hand locally and at the live URL, screenshots in the report), the deploy workflow itself (it is tested by running it), Azure behaviour such as a paused database resuming or the platform's 503 during a cold start (seen in the deploy logs instead), and load.
Update 2026-11-24: CI now also gates on security, and these jobs are required on `main` too. SAST: Bandit over both services; its nine "possible SQL injection" findings were queries built by joining a constant column list or `%s` markers, so the queries became constant strings and `IN` lists one tuple parameter that pymssql expands, and its three `urlopen` findings got a real http(s) scheme check plus a `# nosec` with the reason. SCA: pip-audit over the locked requirements found CVE-2026-27205 in Flask 3.1.2 (a missing `Vary: Cookie`; the services never use Flask's session), fixed by moving to 3.1.3. Image scan: Trivy found seven fixable HIGH vulnerabilities in the Debian packages of the base image (zlib, OpenSSL, pcre2, apt), so each Dockerfile now applies Debian's security updates. Secrets: gitleaks scans every commit and found none. Dependabot proposes updates weekly. Policy as code: Checkov checks `infra/main.bicep`, both Dockerfiles and the workflows; it led to a `HEALTHCHECK` in both images and a Microsoft Entra admin on the SQL server, and the checks that fail on purpose are listed in `.checkov.yaml` with their reasons: the UI storage must stay public, and private endpoints, SQL auditing, Defender for SQL, zone redundancy and geo-replication all cost money or need resources outside the allowance; Entra-only SQL authentication would lock out the services' own users. Eleven checks are required now. Not done: DAST against the running services, and image signing.

## 10. Not built: a queue and worker for Jev and Chef rounds
Date: 2026-11-23
Status: Decided
Context: A round is one Jev call and one Chef step and takes 5 to 28 seconds. Ideas waits for it inside the founder's request (`POST /rounds`, 30 second timeout), and the round holds one of review's eight gunicorn threads (2 workers x 4 threads) for that time. A message broker is outside the assignment's scope, and so is a third container.
Decision: Not built. Rounds stay synchronous: the answer is saved first, review is called with a timeout, and a round that runs over finishes in review and shows on the next page load (ADR 6, ADR 8). With at most one replica and a club of founders, eight threads are enough.
Alternatives considered: A queue (Azure Service Bus or a storage queue) with a worker in review. Ideas would save the answer, put a "score revision N" message on the queue and answer the founder at once; the worker would call Jev and Chef and store the result, and the page would poll for it. This removes the timeout and the held threads, and lets failed rounds retry with backoff instead of waiting for the founder's "retry". It was not built because it adds a broker and a worker process that must be deployed, scaled and observed, a polling or push channel to the browser, and a new failure mode (messages that are never processed), all to fix waits that a small cohort barely notices. A gateway container in front of both services was the other candidate: it would give the browser one origin and hide review, and was not built because it is a third container and adds a hop to every request.
Consequences: Under load the first thing to break is review's thread pool: with more than eight rounds in flight, further requests queue in gunicorn and ideas' 30 second calls start timing out, so founders see "not scored yet" more often. The queue becomes worth building when any of these holds: rounds regularly pass 30 seconds (slower models or a second Jev call), review needs more than one replica (startup migrations would first have to move out, ADR 8), or the cohort grows to where several founders answer at the same moment, which a busy demo day would show first. The seam would not move: ideas would still own the revision and review the verdict; only the call between them would become a message.
